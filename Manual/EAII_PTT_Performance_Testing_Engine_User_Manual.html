2. Testing Engines Used

EAII PTT is engine-aware. The selected engine performs the real workload. EAII PTT must not create fake RPS, latency, VU or error values.

k6

Type: Scriptable load/performance-testing engine.

Why: Good for controlled API scenarios, virtual-user stages, thresholds and structured performance metrics. It is well suited to automated and repeatable load tests.

EAII PTT: Builds the k6 workload, starts the real k6 process and consumes its actual measurements.

Locust

Type: Python-based user-behavior/load-testing engine.

Why: Good when workloads need Python-defined user behavior, tasks and flows, and when interactive Locust monitoring is useful.

EAII PTT: Builds/starts the Locust workload and consumes actual Locust results.

Selection rule: k6 test → k6 execution and metrics. Locust test → Locust execution and metrics. The dashboard must follow the selected engine.

Why VUs do not determine RPS

WRONG:
2000 VUs × arbitrary multiplier = 7000 RPS

RIGHT:
2000 VUs
   ↓
Real k6 / Locust execution
   ↓
Real HTTP requests
   ↓
Real responses
   ↓
Measured request rate = actual RPS

6. Evaluation and Scoring

REAL ENGINE RESULTS ↓ Validate result integrity ↓ Reliability 80% + Performance 20% ↓ SLA / Quality Gates ↓ Final score + status

Reliability — 80%

AreaWeight
Success / failure35%
HTTP 5xx20%
Timeouts15%
HTTP 4xx5%
Consistency / stability5%

Performance — 20%

Uses actual latency and throughput measurements such as AVG, P95/P99 and RPS/throughput according to the configured profile.

Final Score =
(Reliability × 0.80)
+
(Performance × 0.20)

Critical is a quality-gate result

Example:
Score = 84 / 100
P95 = 2800 ms
Critical P95 limit = 2000 ms

Result:
Score  = 84 / 100
Status = CRITICAL

A high numerical score must not hide a hard critical SLA breach.

Zero-data protection: 0 requests + 0 ms latency is NOT Excellent. It means no valid test evidence exists and the result must be treated as incomplete/no-data.

7. Test Lifecycle

Normal completion

START ↓ RUNNING ↓ REAL ENGINE EXECUTION ↓ ENGINE FINISHES SUCCESSFULLY ↓ COLLECT FINAL METRICS ↓ VALIDATE DATA ↓ EVALUATE ↓ SCORE + STATUS ↓ DONE

Stopped or failed

RUNNING ↓ STOP / ENGINE FAILURE ↓ STOPPED / FAILED ↓ INCOMPLETE ↓ NO FINAL SCORE ↓ NOT DONE

Partial measurements can be preserved for diagnostics, but they must not be presented as a completed final performance result.

Multiple tests

STEP 1  Load       → DONE
STEP 2  Stress     → DONE
STEP 3  Spike      → RUNNING
STEP 4  Endurance  → WAITING

The next step should start only after the previous step completes normally with valid final data.

14. k6 Metrics, PromQL and Dashboard Mathematics

This section documents how the live k6 measurements are transformed into the dashboard metrics. The important rule is that these calculations operate on real engine telemetry; they do not generate simulated performance numbers.

REAL k6 REQUESTS ↓ k6 METRICS ↓ Prometheus / time-series data ↓ PromQL aggregation ↓ EAII PTT dashboard ↓ Evaluator ↓ Score + Status

14.1 Target APIs

count by(endpoint) (k6_http_reqs_total)

This groups the request metric by the endpoint label and counts the endpoint time-series represented in the metric data.

Important: the resulting count must not automatically be described as “APIs successfully tested.” It represents endpoint metric series observed in the telemetry. To claim that an API was exercised, the test must establish that traffic was actually sent to that endpoint.

14.2 Overall Live RPS

sum(
  rate(k6_http_reqs_total{testid="RUN-..."}[1m])
)

k6_http_reqs_total is a request counter. rate(...[1m]) estimates the per-second request rate over the selected one-minute window. Summing the resulting rates gives the overall request rate for the selected test.

Request counter ↓ rate over time window ↓ Per-second request rate ↓ sum across relevant series ↓ Overall RPS

14.3 Overall P95 and P99 Latency

P95:
histogram_quantile(
  0.95,
  sum by (le) (
    rate(k6_http_req_duration_bucket{testid="RUN-..."}[1m])
  )
)

P99:
histogram_quantile(
  0.99,
  sum by (le) (
    rate(k6_http_req_duration_bucket{testid="RUN-..."}[1m])
  )
)

Latency histograms represent observed response durations using cumulative buckets. The histogram buckets are aggregated across the selected request series and then histogram_quantile estimates the requested percentile.

PercentileMeaning
P95Estimated latency at the 95th percentile of the observed latency distribution.
P99Estimated latency at the 99th percentile of the observed latency distribution.

Conceptual bucket calculation

Observed latency
      ↓
Assign observation to histogram bucket
      ↓
Aggregate buckets across endpoints
      ↓
Find bucket containing requested percentile
      ↓
Estimate percentile within that bucket
      ↓
P95 / P99

For a percentile φ, the target rank is conceptually:

rank = φ × total observations

The quantile calculation then locates the bucket containing that rank and estimates the value within the bucket according to the histogram representation.

14.4 Overall Error Rate

(
  sum(k6_http_req_failed{testid="RUN-..."})
  /
  sum(k6_http_reqs_total{testid="RUN-..."})
) × 100
Real requests ↓ Request outcome ↓ failed / total ↓ × 100 ↓ Error Rate %

The denominator must represent the real requests included in the same test scope. A zero-request test must not be converted into a successful 0.00% performance result.

14.7 Critical Data-Integrity Rule

Never manufacture a result when telemetry is missing.

For example: 
Requests = 0
P95 = 0 ms
P99 = 0 ms
Error Rate = 0.00%

This does not mean the system performed excellently. It means there is no valid performance evidence. The run should be treated as NO DATA / INCOMPLETE until valid engine measurements exist.

14.8 Separation of Responsibilities

LayerResponsibility
k6 / LocustGenerate real workload and collect engine measurements.
Metrics pipelineTransport/store/aggregate engine telemetry.
PromQLCalculate dashboard views such as rates, grouped counts and histogram quantiles where Prometheus metrics are used.
EAII PTT evaluatorInterpret validated measurements against thresholds, SLA rules and scoring rules.
ReportPresent the measured results, evaluation and final assessment.
Core principle: The engine measures reality. PromQL calculates views of that measured reality. The evaluator judges the measured reality. No layer should invent performance measurements.

10. Troubleshooting

Application does not start

npm install
.
un_windows.bat

concurrently is not recognized

The local npm dependency is missing/unavailable. Run npm install from the project directory and restart.

k6 or Locust is not found

Verify that the corresponding engine is installed and available to the environment used by the startup script.

Dashboard shows 0 RPS / 0 ms

First verify that the selected engine actually started and generated requests. If there are zero real requests, the application must not convert that into Excellent.

Test says Completed but metrics are zero

This is a result-integrity failure. Completion should require successful engine termination plus valid final measurements.
